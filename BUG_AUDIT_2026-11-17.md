## Confirmed findings

All triggers below use temporary stores and fake accounts. They demonstrate
code defects under the stated conditions, not that each condition has occurred
in the user's live history. P2 denotes a normal-priority correctness fix; P3
denotes a lower-priority robustness fix.

### 1. Distinct OpenCode legacy history is omitted when v2 messages exist (P2)

Location: [load_messages](ai-usage/bin/opencode-usage#L456).

The collector chooses the first nonempty source globally: v2 messages, then
filesystem history, then the legacy SQLite table. It does not combine distinct
sessions across those stores. A migration or mixed installation can therefore
silently underreport history from a still-present older store.

Reproduction `test_03`: v2 contributes 6,290 tokens; a distinct filesystem
session contributes 2,000. The collector reports **6,290 instead of 8,290**.
Source records are not deleted. The defect is omission from the calculated
totals, rather than destruction of the native history.

Suggested fix: merge supported sources with stable request/message identity
deduplication. Preserve per-session aggregate guards and avoid counting migrated
copies twice. Add a mixed-store fixture before implementing the change.

This selection logic predates the session-title work and is also present in
the earlier committed standalone collector at `c88e69d`.

### 2. Cached Codex quotas survive an account/login switch (P2)

Location: [cached_rpc and throttled_rpc](ai-usage/bin/codex-usage#L220).

The two-minute cache is bound to elapsed time and output-cache path, without
an account or login-state discriminator. After a successful ChatGPT quota read,
switching to an API-key login inside that window bypasses `account/read` and
continues publishing the previous Plus quota as RPC data. A different ChatGPT
account can similarly retain the previous account's cached measurement.

Reproduction `test_01`: the fake server first reports ChatGPT Plus with 25%
usage. It then reports an API-key account. The second collection still shows
**Plus, 25%, and a five-hour window**. A refresh after cooldown can correct it.

Suggested fix: invalidate the quota cache when its login context changes,
without exposing credentials, and retain the existing authoritative empty
quota response for API-key/Bedrock accounts.

This is a regression relative to the pre-title-work primary snapshot. The
same account-switch check passes against that backup, which had no quota RPC
cooldown. The cooldown was inherited from upstream stable commit `070aa9d89`
while reconciling the source. It is separate from the saved-name lookup.

### 3. Future-dated requests contaminate non-rolling totals (P2)

Locations:
[Claude totals](ai-usage/bin/claude-usage#L183),
[OpenCode sum_since](ai-usage/bin/opencode-usage#L485), and
[Codex history_period](ai-usage/bin/codex-usage#L1134).

Several aggregators enforce a lower cutoff without an upper bound at the
collection time. Clock corrections or imported records dated in the future
can inflate current activity. The exact trailing 24-hour helper does enforce
both bounds, creating disagreement between cards and period selections.

Reproductions:

- `test_05`, Claude: a request two days ahead contributes **1,600 to Today**
  while the Last 24 hours period correctly reports **0**.
- `test_10`, OpenCode: a future request adds **1,600** to a 6,290-token baseline;
  Today reports **7,890 instead of 6,290**.
- `test_06`, Codex: a future request produces **1,000 tokens/hour** and
  **800 uncached tokens in the Today period**, while the Today header and
  Last 24 hours correctly remain **0**. The inclusive versus uncached values
  follow the existing schema; their inclusion in present periods is the bug.

Suggested fix: apply a consistent permitted timestamp range before accounting,
including session, period and spending inputs. Preserve any intentional small
clock-skew allowance consistently across views.

The affected collector functions are unchanged from the pre-title-work backup.

### 4. A stale cache can keep a session visibly running (P2)

Location: [runningSessions](ai-usage/UsageModel.qml#L44).

`runningSessions` trusts the cached flag independently of cache freshness.
When collection stops succeeding after an active turn, opening an old cache
can retain the green running indicator and live-session row.

Reproduction `test_08`: parse a cache whose modification time is an hour old,
with one session marked running. The model reports **fresh=false** but still
exposes **one running session**. The real isolated Qt engine confirms the same
values, so this is not solely an inferred binding issue.

Suggested fix: represent stale session activity as last-known/unknown rather
than asserting that the process is still running. Preserve historical rows.

This binding predates the title work; it is present in initial port `5c9d9f11c`.

### 5. Nested malformed data can stop collection or leave partial UI state

JSON syntax and top-level checks do not validate every nested shape. The
following four cases are independently reproducible:

| Check | Trigger | Observed behavior | Location | Priority |
| --- | --- | --- | --- | --- |
| `test_02` | Codex activity schema 5 contains `seenTokenEvents: ["broken"]` | Collector exits 1 with `AttributeError: 'list' object has no attribute 'items'` | [scan_activity](ai-usage/bin/codex-usage#L609) | P2 |
| `test_07` | Prior Codex cache contains `_hours: [null]` | Collector exits 1 with `TypeError: 'NoneType' object is not iterable`, despite valid native usage | [merge_published](ai-usage/bin/codex-usage#L1272) | P2 |
| `test_04` | One OpenCode v2 message contains `tokens: [1]` alongside a valid message | Collector exits 1 with `AttributeError: 'list' object has no attribute 'get'`; valid messages are not published | [parse_v2_message](ai-usage/bin/opencode-usage#L217) | P2 |
| `test_09` | Cache period contains `models: [null]` | QML logs a parse exception but retains `has=true` and already assigned counters | [parse](ai-usage/UsageModel.qml#L227) | P3 |

The last case is also confirmed in a real isolated Qt engine: after the parse
exception it reports **has=true, today=999**. Either skipping the invalid model
row or rejecting the cache atomically would be coherent; the current catch
leaves a partly applied result.

Suggested fix: validate nested records at ingestion, skip damaged rows without
discarding valid history, and publish UI parse state consistently. Do not
delete retained ledgers to recover from these cases.

These functions are AST-identical, or text-identical for QML, to their versions
in the pre-title-work backup.
